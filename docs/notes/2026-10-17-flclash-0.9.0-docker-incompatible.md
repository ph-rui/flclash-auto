# FlClash 0.9.x 在 headless Docker 里卡在免责声明（核心不启动）

- **日期**：2026-10-19（0.9.0 首次复现 10-17，0.9.1 复核 10-18）
- **环境**：`jlesage/baseimage-gui` + Xvnc + cinit/supervisor，无桌面会话，应用以 uid 1000 运行，`--privileged` + `/dev/net/tun`
- **上游 issue**：https://github.com/chen08209/FlClash/issues/2728
- **结论**：0.9.x 在首次启动时会弹出**免责声明对话框**；`appSettingProps.acceptedDisclaimerVersion < disclaimerVersion` 时，`bootstrap` 的 `_initApp` 停在 `requestDisclaimerConsent()` 并直接 `return`，**根本不会执行 `coreActionProvider.startCore()`**。headless 环境没人点"同意"，于是表现为：app 进程在、UI 起不来、7890 不监听、没有 `FlClashCore`。
- **处理**：`flclash-auto` 在升级/重启前把 `acceptedDisclaimerVersion` 写成 `1`（0.9.0/0.9.1 的 `disclaimerVersion = 1`），之后核心、代理、url-test 改写全部正常。生产已升级到 0.9.1 并验证通过。

## 关键证据

同一台机器、同一份配置：

| 场景 | 结果 |
|---|---|
| 0.8.98（无免责声明逻辑） | 9 秒内启动核心，7890 出网正常 |
| 0.9.1，`acceptedDisclaimerVersion=0` | 6 分钟无核心、7890 不监听；app 日志停在 `connectivityChanged` |
| 0.9.1，`acceptedDisclaimerVersion=1` | 20 秒内出现 `FlClashCore`，`[APP] IPC Connected: <pid>`、`init result: true`，204 正常，出口 IP 正常 |

Windows 版 0.9.1 一直正常，因为桌面上有人点掉免责声明——这也解释了为什么"只有 Linux/Docker 有问题"。

## 之前几个假设为什么不成立

排查过程中试过并否定了：

1. **helper 提权失败**：`FlClashHelperService` 在没有 `/run/flclash` 时确实会退出；补齐目录和 `FLCLASH_HELPER_OWNER_UID/GID` 后可以正常监听 `/run/flclash/helper.sock`。但 app 在 helper 不可用时本来就会回退到直接启动核心，helper 不是根因。
2. **以 root 运行**：`USER_ID=0`（cinit `--default-service-uid 0`）后仍无核心——因为对话框同样在等点击。
3. **TUN 需要特权**：profile 里 `tun.enable` 本来就是 `false`。
4. **核心二进制损坏**：`manifest.json` 的 `coreSha256` 与 `sha256sum /opt/FlClash/FlClashCore` 完全一致；手动运行核心会正常去 connect app 创建的 socket。

## 复现

```bash
# 复制生产数据，独立端口，不影响线上
cp -a ~/flclash-docker/flclash /tmp/t091/data
docker run -d --name flclash-t091 --user 0:0 --privileged --cap-add NET_ADMIN \
  --device /dev/net/tun -v /run/dbus/system_bus_socket:/run/dbus/system_bus_socket \
  -v /tmp/t091/data:/config/xdg/data/com.follow.clash -p 27891:7890 flclash:0.8.98

# 装 0.9.1 并重启，观察 6 分钟：无 FlClashCore、7890 不监听
docker cp FlClash-0.9.1-linux-amd64.deb flclash-t091:/tmp/f.deb
docker exec flclash-t091 pkill -f '/opt/FlClash/FlClash'; sleep 3
docker exec flclash-t091 dpkg -i /tmp/f.deb
docker restart flclash-t091

# 只改这一个字段，再重启：核心立即启动
python3 - <<'PY'
import json
p = '/tmp/t091/data/shared_preferences.json'
d = json.load(open(p))
cfg = json.loads(d['flutter.config'])
cfg['appSettingProps']['acceptedDisclaimerVersion'] = 1
d['flutter.config'] = json.dumps(cfg, ensure_ascii=False)
json.dump(d, open(p, 'w'), ensure_ascii=False)
PY
docker restart flclash-t091
```

## 影响与当前处理

- `flclash-auto` 的行为：健康检查失败 → 标记坏版本 → 回滚 → 不再自动尝试。
- 升级流程在 `dpkg -i` 之后、重启之前调用 `ensure_disclaimer_accepted`：只改 `acceptedDisclaimerVersion`，其它字段原样保留；写失败会直接回滚，不会留下一个"看似升级成功、实际没核心"的容器。
- 回滚会还原升级前的 `database.sqlite` / `shared_preferences.json`（0.9.x 会把库从 45 KB 迁移到 69 KB，只换旧镜像会让 0.8.98 起不来）。
- 若上游未来把 `disclaimerVersion` 提高到 2，本工具写入的 1 将不再满足，升级会因健康检查失败自动回滚并拉黑该版本；届时把 `ensure_disclaimer_accepted` 里的值同步为新的 `disclaimerVersion` 即可。

## 给上游的建议

1. headless/无人值守场景不要让 core 启动依赖 UI 对话框：可以先启动核心，或在无 `DISPLAY`/无交互时跳过或默认接受。
2. 提供一个显式开关（环境变量或命令行参数），例如 `FLCLASH_ACCEPT_DISCLAIMER=1`，供 Docker/CI 使用。
3. 0.9.1 的 Linux 端日志里会周期性出现 `dashboard connections error: Unsupported operation: Cannot modify an unmodifiable list`（约 45 次/分钟），不影响代理，但会持续刷日志，建议一并修复。
